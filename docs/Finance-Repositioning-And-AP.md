# 第一部分 · 总纲

## 1. 决策

原始规划中,UniOps Finance 要逐步完善成一个真正的财务管理模块,**最终替换 NC65 的财务部分**。

现实是:UniOps 还没有**销售、固定资产、生产、库存**这几块,做不成一本完整的账。
在这个前提下继续把 Finance 往「账本」方向推,位置尴尬且不可能成立。

**因此(Justin,2026-09-20 决定):**

> **当前阶段(至少 1 年):一切以 NC 数据为准,UniOps Finance 退化为「财务辅助系统」。**
> NC 财务里的数据全部同步过来,在 UniOps 这里做 NC 做不到的事:各类财务报表、
> 财务数据检查、现金流。

已经在做的 **JV 维度校验**、**预算计划与预实对比**,就是这个定位的产物。

## 2. 定位声明与两条红线

> **NC65 是会计账本(book of record)。UniOps Finance 是建立在 NC 账之上的
> 「财务保障与分析层」—— 它不产生会计分录,它负责把 NC 的数据完整地取过来、
> 验证它是对的、并做出 NC 做不出来的报表与洞察。**

**红线一:UniOps Finance 不做第二本账。**
任何时候有人问「这个数以谁为准」,答案永远是 NC。我们的报表只能是 NC 数据的
重新组织,不能是重新计算出来的另一套余额。

**红线二:业务单据仍然是 UniOps 的。**
PR / PO / GR / 发票 / 付款申请这条链由 UniOps 发起,最终以 AP 导出的形式喂给 NC。
准确表述是:**业务单据我们是主,会计结果 NC 是主**。

## 3. 数据流向(谁是主)

| 数据域 | 谁是主 | 说明 |
|---|---|---|
| 会计凭证 / 科目余额 / 财务报表 | **NC** | 已同步 |
| **应付余额** | **NC** | 2026-09-20 决定,见 §10.1 |
| 采购单据 PR/PO/GR/发票 | **UniOps** | NC 导入的 PO 除外(NC 主) |
| 供应商 **账期(payment terms)** | **UniOps** | 见 §10.2 —— 少数「我们该当主」的字段 |
| 供应商主数据(其余) | NC | 我们只镜像 |
| 科目表 / 成本中心 / 辅助核算维度 | **NC** | 我们只镜像,**不提供编辑入口** |
| 客户 / 销售 | NC | UniOps 无此模块 |
| 预算计划 | **UniOps** | NC 无此能力 |
| 付款执行 | UniOps 发起 → NC 记账 | 见 §10.1 的重要例外 |

**规矩:凡是 NC 有的主数据,NC 就是唯一来源,UniOps 只镜像、不编辑、不新建。**
例外必须像「账期」这样在本表里显式列出并说明理由。

## 4. 第一顺位用户

AP / AP Clerk、Payment Officer、Finance Manager、Finance BP。

| 角色 | 主要诉求 | 落在哪层 |
|---|---|---|
| AP / AP Clerk | 三单匹配、重复付款、发票到期、异常发票 | L2 检查 |
| Payment Officer | **现金流、资金头寸、银行余额**、付款批次 | L3 报表 |
| Finance Manager | 三大报表、结账、对账、合规留痕 | L2 + L3 |
| Finance BP | 预实对比、部门成本分析、预算占用 | L3 + L4 |

**推论一:这四个角色都是天天使用的操作者,没有「看板观众」。**
→ 优先级是 **L2 检查层、L3 报表层 > 漂亮的 dashboard**。

**推论二(矛盾,待解):** Payment Officer 要的资金头寸是「当下能不能付」,
而同步频率定的是一天一次(§5.2)。这块可能需要更高频次,或者绕开 NC 直接用银行流水。

## 5. 能力分层与同步

### 5.1 L0–L4

| 层 | 内容 |
|---|---|
| **L0 镜像层** | 把 NC 财务数据全量同步过来(凭证、科目、余额、辅助核算、往来、资产)+ 完整性对账 |
| **L1 主数据对齐层** | 科目表、成本中心、维度、往来单位的映射与漂移检测 |
| **L2 保障层** | NC 没有的「检查」:维度校验、借贷平衡、往来对账、异常凭证、跨期、重复付款、主数据漂移 |
| **L3 报表层** | NC 做不出来的:三大报表管理口径、**现金流**、多维分析、趋势、部门/成本中心视角 |
| **L4 计划层** | 预算编制、预实对比、滚动预测、资金计划 |

### 5.2 同步时效

- 参照现有 **JV 同步调度器**的做法:可配置同步时点,**一天一次**即可。
- **每个同步域必须提供手动增量同步按钮。**
- 建议做成**统一的「NC 同步中心」**页面:每个同步域一行,显示水位、上次同步时间、
  上次结果、待处理错误数,右侧「增量同步 / 全量重载」。单域页面上的按钮调同一套后端。
- 三个必须内建的机制:
  1. **并发保护** —— 手动与定时不能同时跑同一个域
  2. **跳过即失败** —— 不允许静默 continue(历史上因此永久丢失过 5 张 PO)
  3. **每张报表显示「数据截至 xx 时间」** —— 一天一次的时效下,不写这个必然有人拿昨天的数当今天的

## 6. 工程红线:镜像完整性

做辅助系统,**最致命的不是算错,是悄悄少了**。算错用户会发现,少了不会。

过往事故几乎全是这一类:JV 校验 INNER JOIN 导致整行消失;供应商挂在贷方应付行
导致费用行永远 No Vendor;NC 同步遇到查不到供应商直接跳过**且不退水位**;
删除重建的墓碑占号让水位永远越过;导出时 `=` 开头的文本被当公式整条丢弃。

**因此下列三条写入开发规范,不是愿望:**

1. 每个镜像表必须有**与 NC 的 tie-out 检查**(行数、金额合计、按期间/科目分组的合计),
   定时执行,不平就开任务、发通知。
2. 任何报表取数,**被过滤掉的行必须被计数并可查**,禁止静默丢弃。
3. 增量同步的「跳过」一律记为**可见的失败**,不允许 continue。

## 7. 本次定位连带产生的变更

| 事项 | 结论 |
|---|---|
| `budget_ledger` 表 | **判死刑**。Actual 只认 NC 已记账凭证,该表没有存在理由 |
| 预算占用 / 在途承诺 | 概念保留,改为**派生视图**,不再落一张会漂移的账簿表 |
| 超预算告警 | **只展示不控制**(保守做法),判定口径暂不并入承诺 |
| QuickBooks 镜像 | 上一代遗留,归入 Settings,随 QBO 退役一起删 |
| 科目表 / 税码等 NC 主数据的配置页 | 应改为**只读镜像查看页**,取消编辑入口 |

**`budget_ledger` 删除前必须数清消费者**(此类疏漏已发生四次):
`Total Committed` 卡片、budget-api 的 `actual_by_month`/`actual_year` 及前端类型、
Budget 导出页面第二行 `actual(docs)`、`lineage.py::_operation_mix` 与
`models/ledger.py` 的 `ACTUAL_OPS`/`COMMIT_ADDS`/`COMMIT_RELEASES`、
以及 15,828 行期初数据(合计 7,795,791.51)。

## 8. 复审与退出条件

本定位的有效期是「至少 1 年」。下列任一条件成立时应重新评估:

- UniOps 具备了销售 / 库存 / 生产 / 固定资产模块,能形成完整的会计闭环
- NC65 的维护成本或合规风险高到必须替换
- L0 镜像层的 tie-out 长期稳定,证明我们有能力承接账本

**为了不把路走死:L0 镜像的表结构应当按「将来能当自己的账」来设计**,
只是现阶段数据从 NC 灌进来。这样将来是切换数据源,而不是推倒重来。
这几乎不增加当前成本。

# 第二部分 · 应付篇

> 本篇的全部结论来自 2026-09-20 对 NC65 生产库(只读)与 UniOps 生产库(只读)的实测,
> 取数口径见附录 A,原始数字见附录 B。

## 9. NC 应付的真实结构

### 9.1 四条链

**链 A —— NC 导入的 PO / 原料包材(到货当月即有发票)**

```
采购订单 PO-010-2606-01
  → 到货单 DH...(每次到货一张)
    → 库存采购入库单 CR...(+ 报检单 → 取样单 → 检验单,质检链,非财务)
      → 采购发票
        → 采购结算单 JS...          ← 入库单与发票在此结算匹配
          → 应付单 D1...
            → 采购入库单 I1...      ← 存货成本侧
              → 付款单 D3...
```

**链 B —— 同上,但到货当月没有发票(走暂估)**

```
库存采购入库单 CR2026031100030119   (金额 8,768.09)
  → 暂估应付单 23C1...514   +8,768.09      (3 月)
    → 暂估应付单 23C1...527  −8,768.09      (4 月冲回,摘要 "Estimated Back Offset")
  → 采购发票 → 应付单 D1...8295  9,608.09   (与暂估差 840.00)
```

要点:**暂估挂在「库存采购入库单」上,不是到货单**;冲回是**独立一张负数单**;
暂估金额 = 入库单行金额(实测两边一致)。

**链 C —— 奶**

```
采购订单 → 到货单 →(数据层断开)
财务另建:奶成分采购入库单 → 采购发票 → 应付单 → 付款单
```

**链 D —— UniOps/EPMS 的采购**

```
(EPMS: PR → PO → GR → 发票) → 财务在 NC 手工建应付单 → 付款单
```
**没有暂估环节**;付款单可以跨月。

### 9.2 应付单其实是两个世界

2025–2026 年全部应付单:

| 交易类型 | 来源系统 | 张数 | 是什么 |
|---|---|---|---|
| `D1` | 4(供应链自动,由结算单生成) | 348 | 原料包材 **+ 奶** |
| `F1-Cxx-017` | 1(财务手工建) | **4,604** | 杂项采购 / 费用 |
| 其它(`D1`/1、`F1-Cxx-008`、`F1-Cxx-015`) | 1 | 16 | 零星 |

**93% 的应付单是财务手工敲进去的**,没有任何上游单据。
这正是 Justin 的原话「NC 对这类杂项采购没有对应流程,这也是我开发 EPMS 的原因」
在数据上的体现。

**推论:EPMS 采购在 NC 里混在这 4,604 张手工单里,与其它费用单形态完全相同。**
要识别只能靠发票号 / 供应商回查 UniOps。

### 9.3 ★★ 凭证与业务单据之间没有数据库关联

这是本篇最重要的一条,它决定了所有对账方案的做法。

- 2026 年共 **6,043 张凭证**,`GL_VOUCHER.PK_SOURCEPK` 与 `GL_DETAIL.PK_SOURCEPK`
  **全部为空(`~`)**。
- `PK_SYSTEM='AP'` 只表示「这张凭证归属应付模块」,**不指向是哪张应付单**。
- **唯一可用的钥匙是摘要(EXPLANATION)里人工写的发票号。**
  而 InvoiceNo 在 NC 应付单上是**必填**,因此这把钥匙一定存在。

**实测可行性:2026 年 8 月有发票号的应付单 321 张,其中 319 张能在凭证摘要中
按发票号匹配到,命中率 99.4%。**

**但必须模糊匹配。** 摘要是自由文本,发票号会与前缀粘连,例如:

```
Received  Invoice0000396CA01C100712219 E&Y service to prepare and filling of 2025…
```

→ 实现要求:去空格 + `instr` 包含匹配,**禁止等值匹配**;
→ **「匹配不上」只能判定为「待人工确认」,不得直接判定为「未记账」**(见 §12 的验证纪律)。

### 9.4 凭证上的辅助核算维度

实测一张费用凭证(6602 管理费用行)的辅助核算为四项:

| 序号 | 维度 | 主数据表 | 本例取值 |
|---|---|---|---|
| 0001 | 部门 | — | Finance |
| 0008 | **收支项目** | `BD_INOUTBUSICLASS` | `CRM00601` 财务咨询费 |
| 0010 | 项目 | — | **空** |
| 0019 | 供应商档案 | `BD_SUPPLIER` | E&Y |

**★ 成本中心是「按科目配置」的辅助核算项,不是所有分录都有。**(2026-09-21 修正,
初稿据单张凭证误判为「NC 凭证上没有成本中心」,不成立。)

2026 年 GL 明细 66,526 行:5,168 行无任何辅助核算;61,358 行有;其中 **11,634 行(19%)带成本中心槽位,
且槽位为空的有 0 行** —— 有就一定填了。按科目看:

| 科目 | 行数 | 带成本中心 |
|---|---|---|
| `5101` 制造费用 | 7,644 | **100%** |
| `5005` | 3,654 | **100%** |
| `5003` / `5001` | 253 / 83 | **100%** |
| `6601` 销售费用 | 3,396 | **0%** |
| `6602` 管理费用 | 2,157 | **0%** |
| `1403`/`2202`/`2225`/`1406`/`1002` 等 | — | **0%** |

**结论:生产制造类科目(5xxx)带成本中心且 100% 覆盖;期间费用类(66xx)只有部门 + 收支项目。**

→ 现行 `nc_sync.py` 的 `CC_BY_CODE` / `CC_BY_DEPT` 映射,本质是在给 6601/6602 **合成**
  一个 NC 不存在的成本中心。这是一个**派生值**,不是 NC 的事实。
  **凡展示该值处必须标明「派生」**,否则违反红线一。
→ 待决(§14.1)因此不是「改成部门还是成本中心」的二选一,而是:
  **5xxx 用 NC 的真成本中心,66xx 用(部门 × 收支项目)或标注派生的映射值。**

### 9.5 暂估

- 表:`AP_ESTIPAYABLEBILL` / `AP_ESTIPAYABLEITEM`,单据类型 `23C1`,共 944 张
  (2020-08-30 ~ 2026-09-11)。
- **暂估行上没有科目(`SUBJCODE`)、也没有成本中心(`COSTCENTER`),只有部门。**
- 冲回是独立一张负数单,不是修改原单。
- **另有一套并行的手工 JV 暂估**(凭证摘要如 `Reverse the accrued payable JV#779-Dec 25`)。
  → 统计「该暂估 / 已暂估」时**两套都要算**,只看 `23C1` 会漏。

**由暂估推出的口径:**
「已收货未开票」对**链 A/B(原料包材)** 而言已经在 NC 的已记账实际里了,
不属于在途;但对**链 D(EPMS 采购)** 不成立 —— 链 D 没有暂估环节,详见 §14 待决事项。

### 9.6 费用发票与价值调整

NC 采购发票分两类(2025-01 起):

| 类型 | 张数 | 说明 |
|---|---|---|
| `25-01` Inventory Invoice | 267 | 正常采购发票 |
| `25-05` Expense Invoice | **59** | 费用发票(运费、报告费等杂费) |

费用发票中:
- `BFEE='Y'` **14 张** —— 挂在正式发票之下(`PK_PARENTINVOICE` 有值),**正规做法**
- `BFEE='N'` **45 张** —— **parent 全部为空,孤儿,占 76%**

**成因(Justin):** 正式发票还没到、费用发票先到,财务无法使用「关联费用发票」的方式建单,
只能单独建。后果是「很多 Invoice 没有上流单据(PO),一个纯 Invoice 凭空出现」。

**但 45 张孤儿其实是两类,检查工具必须分开处理:**

| 供应商 | 张数 | 金额 | 实质 |
|---|---|---|---|
| RADIANT GLOBAL LOGISTICS | 32 | +21,786.87 | 货代运费 —— **真·流程问题** |
| KLN (Kerry Logistics) | 3 | +785.58 | 同上 |
| **Dairy Farmers of Ontario** | **9** | **−87,468.52** | 奶成分结算的价差调整 —— **正常机制,不是异常** |
| Great Lakes Goat Dairy | 1 | −10.00 | 同上 |

→ 不分开的话,检查工具每月会稳定产出 9 条以上假警报。

**孤儿费用发票的归宿:财务手工建凭证做价值调整。**

实测 2026 年打到 `14xx` 存货科目的凭证:

| 来源系统 | 凭证数 | 分录行数 | 借方合计 |
|---|---|---|---|
| **GL(手工)** | **107** | **21,408** | **22,424,938.38** |
| IA(存货核算) | 128 | 2,812 | 3,712,345.42 |
| AP | 261 | 470 | 4,486,248.79 |
| CM | 27 | 76 | 23,607,681.48 |

手工凭证摘要样例:`Jan 2026 CBSA Custom Duty Ind Can 057-2510-01B  138.37`
—— **海关关税按 PO 批次逐行分摊,每行一两百元,单张凭证数百行,全年逾 2 万行纯手工录入。**

**★ 重要警告:摘要里的 PO 号不是权威数据。**
现行做法是**人工模糊识别**:拿报税金额去 PO 里凑金额,推断「大概来自哪个 PO」。
因此这些 PO 号是**人工推测的结果**。
→ **关税分摊链不得进入检查工具的自动判据**,只能做展示与人工辅助。
→ 关税问题(Justin 称之为「天坑」)**单独立项讨论**,不在本篇范围。

**价值调整的时效风险(Justin 确认:一般当月做,但有遗漏,发现了再补):**

物料出库在财务侧只有三条路径,一旦走完,迟到的价值调整就无法落到正确的对象上:

| 出库路径 | 迟到的价值调整会怎样 |
|---|---|
| 生产消耗单 → 成本计算 → **产品成本** | 产品成本已结转,改不回去,只能进当期损益 |
| 其他部门领用(QA 样品检测 / 工程非设备类易耗品 / 市场赠品与销售耗材) | 已进各自费用科目,同上 |
| 储运损耗、报废 | 已进专门会计科目,同上 |

> 注:部门领用类单据是月结时系统生成临时单据、人工调整后生成正式单据。

→ **因此检查项必须是「月结锁账前拦截」,而不是「事后发现遗漏」**(§12 判据 5)。

### 9.7 奶

奶的链在 NC 数据层就是断的,且**这是业务本身决定的,不是数据缺陷**。

同一张表 `IC_PURCHASEIN_B` 的两种入库单对比:

| 单据 | `VSOURCEBILLCODE` | `VFIRSTBILLCODE` | 批次号 | 金额 |
|---|---|---|---|---|
| 包材入库 `CR2026031100030119` | `DH2026031100024227`(到货单) | `PO-057-2511-01` | 2601-J000020036 | 8,768.09 |

奶成分采购入库单:仓库 `Raw Milk Component`,出入库类型「生牛乳按组分入库」,

**成因(Justin):** 奶按**奶量**采购、按**成分**结算;月底把当月多张牛奶 PO 涉及的成分

**口径结论:**

- 当月到货奶量 ↔ 成分入库量的闭环校验
- 每公斤乳脂 / 乳蛋白 / 其他固形物的单价走势
- 奶量到成分的转化率分析

2026 年奶类供应商应付规模:Lactalis Canada 1,785,994.58(10 张)、
Dairy Farmers of Ontario 1,208,447.41(17 张)、Ontario Dairy Goat Co-operative 408,548.76(5 张)。

## 10. 口径定义

### 10.1 ★ 应付余额以 NC 为准

**决定(Justin,2026-09-20):应付余额一律以 NC 的 `AP_PAYABLEITEM.MONEY_BAL` 为准。
UniOps 不再自行维护一套「未付」。**

**依据 —— 三方对账实测。** 取 UniOps `ap_invoices` 中 `status='posted'` 且有发票号的
258 张,逐张按发票号到 NC 比对:

| 对账结果 | 张数 | UniOps 挂账未付额 |
|---|---|---|
| NC 也未结清(真欠) | 148 | 431,885.93 |
| NC 中找不到(NC 尚未入账) | 79 | 198,170.43 |
| **NC 已结清、UniOps 仍挂账(虚高)** | **31** | **129,023.71** |

**根因:付款在 NC 发生,不回流到 UniOps。** 例:CCIC `2026000065` 36,465.78、
Summa Strategies `12227` 22,600.00、CCIC `2026000071` 19,224.92,NC 均已结清,
UniOps 仍为 `posted`。

→ 任何基于 UniOps `paid_amount` 的应付余额或现金流**都会虚高**。
→ **`ap_invoices.nc_exported_at` 全库仅 10 张有值**,AP 导出功能几乎未被使用,
   **不得用它判断「是否已交给 NC」**。

**同时,「UniOps 有发票而 NC 中没有」的性质也随之改变:**
它不再是对账差异,而是 **NC 账上缺失的负债**(79 张 / 198,170.43),
应作为检查工具的第一屏,同时构成 Cash Flow 的 L2 层。

### 10.2 到期日

**决定(Justin,2026-09-20):**

1. 发票上有明确账期 → 用发票的
2. 否则 → 用**供应商主数据**中维护的账期
3. 供应商也没有 → **标记为「账期未知」单独列出,不得静默回落到 30 天**

**账期的主数据归属:UniOps**(见 §3 的例外说明)。
理由:NC 不消费这个字段(它连到期日都算不出来),UniOps 是唯一消费者。

**现状(必须先治理):**
- UniOps `vendors.payment_terms`:**752 家供应商全部是 `net30`**,无一例外
- 因此现行 `ap_invoices.due_date` 实际上就是「发票日 + 30 天」(464 张中 418 张正好差 30 天)
- NC `BD_SUPFINANCE` 也挂账期,实际也只用了一种

→ 需在供应商主数据上提供账期编辑入口,并对「仍为默认 net30」的供应商做提醒,
  否则维护不会真正发生。

### 10.3 期间与记账状态

所有应付相关报表必须显式声明并在页面上显示三件事:

1. **会计期间**
2. **是否包含未记账凭证**(NC 界面含未记账,我们只取已记账,两边天然对不上)
3. **是否包含年结凭证**

另:暂估冲回会在次月产生负数发生额,**这是正常机制而非异常**,报表需加注说明。

## 11. 应付 Cash Flow 设计

### 11.1 为什么 NC 出不了这张表

**NC 的应付单上没有到期日字段。** `AP_PAYABLEBILL` / `AP_PAYABLEITEM` 只有
`BILLDATE` / `BUSIDATE` / `APPROVEDATE` / `EFFECTDATE`,加一个 `PK_PAYTERM`(付款条件)。
界面上的 `due date` 是自定义字段,实测为空。

更关键的是付款条件覆盖率:

| 应付单类型 | 未结清行数 | 未结清金额 | 有账期 |
|---|---|---|---|
| 手工 `F1-Cxx-017` | 382 | 2,263,180.23 | ✅ 全有 |
| 供应链 `D1`(奶 + 原料) | 53 | **1,924,887.60** | ❌ **全无** |
| 其它 | 2 | 350.00 | 部分 |
| **合计** | **437** | **4,188,417.83** | |

**46% 的未付金额连推算到期日的依据都没有。**

而 UniOps 侧 258 张 posted 未付、774,942.30,**100% 有到期日**。

> **这就是 UniOps 在应付这块最清晰的价值主张:金额以 NC 为准,到期日与资金计划由 UniOps 提供。**

### 11.2 五层结构

一个总数无法回答「未来资金需求」,因为各层确定性差异很大。按层呈现,每层标注可信度:

| 层 | 内容 | 金额来源 | 到期日来源 | 现状 |
|---|---|---|---|---|
| **L1** | NC 已记账未结清 | **NC `MONEY_BAL`** = 4,188,417.83 | 能匹配上的用 UniOps `due_date`;匹配不上的按 §10.2 推算 | 可做 |
| **L2** | UniOps 有发票、NC 未入账 | UniOps 发票 = 198,170.43 | UniOps `due_date` | 可做 |
| **L3** | 已收货未开票 | GR × PO 单价 | 预计账期 | 需定义(见 §14.2) |
| **L4** | 已下单未收货 | PO 未收部分 | 交期 + 账期 | 需定义 |
| **L5** | 周期性协议(租金等) | `agreement_payment_schedule` | 协议约定 | 可做 |

**奶单列一层**:月度成分结算,规律性强,按月预测比逐单更准。

**可能有用但尚未细查的 NC 资源:** `PO_ORDER_PAYPLAN`(采购订单付款计划,14,992 行)、
`PO_ORDER_PAYMENT`(5,695 行)。

## 12. 应付链路检查工具(「每个单子有头有尾」)

### 12.1 实施顺序(Justin 2026-09-20 确认)

| # | 检查项 | 判据 | 数据是否就绪 |
|---|---|---|---|
| **1** | **UniOps 有发票、NC 没有** | 按发票号在 `AP_PAYABLEITEM` 与凭证摘要两处均未命中,且金额+供应商二次确认后仍未命中 | ✅ 现有数据可跑,当前 79 张 / 198,170.43 |
| **2** | **发票号不一致** | 金额与供应商一致、发票号不一致 | ✅ 可跑,已抓到 2 起(见 §12.3) |
| **3** | **应付超账期未付** | NC `MONEY_BAL<>0` 且推算到期日 < 今天 | ✅ 可跑(依赖 §10.2 的账期治理) |
| **4** | **该暂估未暂估** | 入库单已过账、当期无发票、且 `23C1` 与手工 JV 暂估**两套**均无对应 | ⚠️ 需先确认手工 JV 暂估的识别规则 |

| **6** | **发票日期异常** | 到期日 < 发票日期,或发票日期为未来日期 | ✅ 可跑,当前 3 张(见 §12.4) |

**排除规则:**
- 判据 5 必须**排除奶类供应商的负数费用发票**(Dairy Farmers / Great Lakes Goat),
  那是正常的成分结算调整,否则每月产生 9 条以上假警报。
- 关税分摊链**不纳入自动判据**(§9.6)。

> **「匹配不上」不等于「不存在」。任何否定性结论必须经过金额 + 供应商的二次确认。**

这条不是原则性表述,是实测教训 —— 见下一节。

### 12.3 判据 2 的实测产出(已抓到的真实问题)

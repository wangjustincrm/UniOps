# UniOps Finance 模块 —— 全模块产品需求文档(PRD)与项目现状

> 版本:v1.0(2026-07-13)· 用途:供财务团队整体评审 Finance 模块的范围、业务规则与建设现状
> 范围:UniOps 自建 Finance 模块**全部子模块**(会计内核 / 总账凭证 / 应付 / 应收 / 付款 / 银行对账 / 税务 / 预算),外加从用友 NC65 的历史数据迁移
> 说明:面向业务审核,重点是**业务需求与规则**,技术细节从略。带 ⚠️ 的是**需要财务确认**的点。总账凭证(JV)与 NC65 迁移另有专项详版文档《Finance-Module-PRD》,本文只做概述并指向。

## 1. 文档目的

之前的《Finance-Module-PRD》只覆盖了「引入总账凭证系统」这一件事。本文补齐**整个 Finance 模块**的全景:预算、应付、应收、付款、银行、税务这些**已建成或在建**的部分,和新做的总账内核放在一起,让财务能一次看清「UniOps 的财务系统到底有哪些能力、每块做到什么程度」。

一句话定位:**UniOps Finance 是一套面向北美运营的自建财务中台**,底层用一条「记账脊梁」把所有业务单据统一成会计分录,向上支撑预算、应付应收、付款、税务申报、总账与报表,并承接 NC65 的历史数据。

### 2.2 服务边界(技术实现,财务可略读)

- **finance-api**:会计内核、COA、期间、JV、AP、AR、付款、银行、税务申报。是财务的核心服务。
- **budget-api**:预算目录、计划、因子、预算执行台账。独立服务,通过成本中心与科目和 finance 打通。
- **mdm-api**:主数据(供应商/客户/物料/职员/**税码**)。税码在这里维护,Finance 页面调用。
- **epms / oa**:业务前台(采购/报销),产生单据后推给 finance 记账。
- **前端**:独立的 Finance 前端应用(多页签),财务在一个界面里切换应付/应收/总账/银行/预算等页面。

### 2.3 核心设计原则

- **一切以记账脊梁为准**:应付计提、付款、报销、收入确认……每一笔都写成「事件 + 借贷分录」;科目余额、税表、报表都从这里派生,不各算各的。
- **本位币 = 加元 CAD**;支持多币种交易,保留原币 + 本币双额 + 汇率。
- **科目沿用 NC 中式科目体系**(与集团口径一致、历史零重映射);北美税务(HST/GST/PST)用**税码**表达,不改科目结构。
- **UniOps 是 NC 历史数据的忠实容器**,但不复制 NC 的中式法定处理(强制现金流量项目、金税发票等)。

## 3. 会计内核:记账脊梁(Posting Spine)

这是全模块的地基,财务通常看不到它,但每张单据背后都靠它。

- **记账事件(Posting Event)**:每张业务单据在关键时点(如发票「已过账」、付款「已完成」)产生一个事件。事件对(单据类型 + 单据号 + 事件类型)**唯一**——同一张单据的同一动作只入账一次(幂等,防重复记账)。
- **记账分录(Posting Line)**:事件下挂借贷分录,每行带:科目、借/贷金额(金额恒为正,方向靠借贷)、币种/汇率、税码,以及**辅助核算维度**:成本中心、部门、往来单位、存货/批次/仓库/项目/渠道等。
- **约束**:一行不能同时有借和贷(借贷分列),从数据层防错账。
- **辅助核算维度可扩展**:高频维度(成本中心、部门)直接做成分录字段;长尾维度(收支项目、销售类型、国别、银行账户、自定义)进「辅助维度表」。哪个科目挂哪些维度,由 COA 上的配置决定。

⚠️ **需确认**:这套「事件即入账、单据唯一、借贷分列」的机制是财务后续所有报表/税表的根,财务无需操作它,但需理解**报表数字都来自这里**——若某单据没记账,报表就不体现。

## 4. 会计科目(COA)与会计期间

### 4.1 会计科目表(Chart of Accounts)
- 科目含:编码、名称、科目类型(资产/负债/权益/收入/费用)、余额方向、是否明细科目(末级可记账、上级为汇总)、上级科目、**辅助核算项**(该科目要求挂哪些维度、是否必填)。
- NC 平价元数据:数量核算、默认计量单位/币种、启用起止期、现金流量类别、助记码等——为忠实承接 NC 保留。
- **科目映射桥(Account Mapping)**:把业务口径映射到会计科目——
  - `line_role`:把「应付/银行/进项税」等分录角色对到具体科目;
  - `budget_account`:把**预算科目**对到**会计科目**(预算↔会计的桥,支撑 Budget Actual)。
- 财务在 **Chart of Accounts** 页维护;NC 迁移已导入 360 个科目。

### 4.2 会计期间(Fiscal Period)
- 期间状态:**开启 / 软关(soft close)/ 硬关(hard close)**;没有期间行 = 默认开启。
- **控制关口**:期间非开启会**挡住付款执行**(唯一的「钱出去」闸口);总账阶段会把「挡住过账」也纳入。
⚠️ **需确认**:软关/硬关的界定与谁有权关期?月结节奏?

## 5. 总账凭证(JV)与科目余额表(概述)

> 详细业务规则见专项文档《Finance-Module-PRD》;此处只给全景定位。

- **总账凭证(记账凭证)**:每笔业务自动/手工生成一张凭证;生命周期 **制单(草稿)→ 审核(职责分离 SoD)→ 过账**,支持**弃审、反过账、红冲**;**只有已过账凭证进总账/报表**。
- **科目余额表**:期初 / 本期借方 / 本期贷方 / 期末(本位币),支持①科目余额②按辅助核算(部门/成本中心/收支项目)展开③凭证钻取④与 NC 对账。
- **Budget Actual(预算实际)**:从科目余额按成本中心归集实际发生额,供预算 vs 实际(详见 §11)。
- **NC65 迁移**:加拿大皇家妙克账簿的全部历史凭证已导入,**逐科目余额与 NC 对账 0 差异**;COA、三维辅助核算同步导入。

现状:**JV 与科目余额表后端完成、测试通过、API 可调**;NC 迁移在本地环境验证完成(未动生产);**前端「凭证中心 / 科目余额表」页面待建**。General Ledger 页目前是总账入口的占位。

## 6. 应付账款(AP)

**定位**:UniOps 是应付发票的**主数据中心**。EPMS(采购)与 OA(费用)上传供应商发票,两边各留自己的工作表,finance 按(来源 + 来源单据号)**归一**成标准应付表头 + 税行。

- **应付发票**含:应付单号、来源、供应商、供应商发票号、金额/税额/合计/已付、币种、发票日/到期日、状态、关联 PO。
- **三方匹配**:PO ↔ 收货 ↔ 发票(含发票多 PO 行级分摊)在 EPMS 侧完成,结果同步到 finance 应付。
- **入账**:发票「已过账」时计提应付(借 费用/进项税 贷 应付账款);付款时冲应付(见 §7)。
- **状态**:草稿 / 已过账 / 部分付款 / 已付 / 作废。
- **税行**:按税码拆分,标记是否可抵扣(recoverable)——喂给 GST/HST 申报的进项侧(§9)。
- 财务在 **Accounts Payable** 页查看应付列表与账龄(Aging)。

现状:**已上生产**(供应商发票、三方匹配、付款、应付主数据、账龄)。
⚠️ **需确认**:应付计提的时点(发票过账即计提 vs 审批通过即计提)是否符合你们做法?

## 7. 应收账款(AR)

**定位**:目前**没有销售/CRM 模块**,所以 AR 的发票单据暂由**财务持有**(初级框架)。将来有 Sales 模块后,它成为记录源、finance 转为镜像(与 AP 同一套模式)。

- **应收发票(AR Invoice)**含:发票号、客户、税前金额/税额/合计/已收、币种、发票日/到期日、状态、税行(按税码拆,喂 GST/HST 销项侧)。
- **收款(AR Receipt)**:客户回款是独立单据(幂等),可核销到某张发票,也可挂账(on-account,暂不指定发票)。
- **入账**:
  - 收入确认(发票过账):借 应收账款 / 贷 收入 / 贷 销项税;
  - 客户收款:借 银行 / 贷 应收账款。
- 状态:草稿 / 已过账 / 部分收款 / 已收 / 作废。
- 财务在 **Accounts Receivable** 页操作。

现状:**框架已建**(应收发票 + 收款 + 收入确认 + 收款入账 + 前端页)。这是**初级 AR**——够记录与收款,尚无信用管理、对账单、催收、销售集成。
⚠️ **需确认**:当前谁开应收发票?是否需要客户主数据先接入(见 §12)?AR 的优先级(等 Sales 还是先手工用起来)?

## 8. 付款(Payments)与付款批次

**定位**:一个**统一付款出口**——不管是采购付款单(PA)、直付、还是报销,都走同一个执行器,统一做「能不能付」的校验、记账、回写。

- **付款执行器**统一做:权限/职责分离校验 → **会计期间闸口** → 生成付款事件与分录(借 应付/员工报销应付 贷 银行)→ 回写单据已付金额/状态。
- **付款记录(Payment Record)**:通用单据引用(付款单 PA / 直付 / 报销…),记付款日、方式(EFT/支票/电汇/其他)、金额、币种、出款银行账户、批次号。
- **付款批次 / 跑批(Payment Batch)**:把多张已批准的应付单**打包一起付**,执行时逐张过统一执行器,并给每笔付款打上批次号。财务在 **Payment Batches** 页操作。
- **多币种**:付款保留原币 + 本币 + 汇率。

现状:**已建**(统一执行器、付款记录、付款批次、出款银行选择、期间闸口)。
⚠️ **需确认**:付款方式清单、批次审批与出纳复核流程是否够?

## 9. 银行与对账(Bank & Reconciliation)

- **银行账户(Bank Account)**:银行账户或**信用卡**(信用卡记为负债科目「信用卡应付」,银行记为现金资产);每个账户绑定 COA 科目、币种,并可保存**对账单 CSV 列映射模板**(方便反复导入同一家银行的对账单)。
- **对账单流水(Bank Transaction)**:金额**带符号**(负=出账);导入按(账户+日期+金额+摘要+参考)哈希去重,防止同一份对账单重复导入。
- **对账**:对账单流水与付款记录匹配,状态 未匹配 / 已匹配 / 排除;财务在 **Bank Reconciliation** 页做。
- **汇率(Exchange Rate)**:按币种对 + 生效日维护;支撑多币种交易折算本币。
- 账户与列映射在 **Bank Settings** 页维护。

现状:**已建**(账户、CSV 导入 + 去重、对账工作台、信用卡账户、FX 汇率)。
⚠️ **需确认**:对账是否要求逐笔匹配到付款/收款?差异如何处理?是否需要银行日记账/现金流量?

## 10. 税务(Tax)

- **税码主数据(Tax Code / Tax Rule)**:在 mdm-api 维护,财务通过 **Tax Settings** 页管理(HST/GST/PST 及税率)。采购/应付/应收/报销都读同一套税码;PO/PA/发票记录税码 + 税率快照。
- **GST/HST 申报表(Return Worksheet)**:按会计期间自动汇总——
  - **进项税(ITC)**:来自应付计提与报销付款的进项税分录(可抵扣侧);
  - **销项税(Output Tax)**:来自 AR 收入确认的销项税分录;
  - **净税 = 销项 − 进项**(负数=退税/留抵);
  - **未编码税(tax_code 为空)**单独列为「申报前需补编码」的例外;
  - 支持 **CSV 导出**。

现状:**已建**(税码 CRUD + 页面、GST/HST 申报底稿 + 导出)。
⚠️ **需财务核对**:税码体系是否齐全覆盖 HST/GST/PST 及各省?申报口径(现金制/权责制)、申报周期是否匹配?

## 11. 预算(Budget)子模块

预算是 Finance 里**最成熟**的一块(先于总账建成、已上生产)。

### 11.1 预算目录(Catalog)
- 两级:**L1 预算类别** → **L2 预算科目**,全公司共享(描述「公司为哪些事项做预算」,不含金额)。
- L2 科目可开**因子分解(decomposition)**:该科目的金额不直接填,而是按因子组合拆(见 11.3)。
- 财务在 **Account Catalog** 页维护。

### 11.2 预算计划(Plan)——按成本中心编制
- 一份计划 = 某**成本中心 × 财年**的预算;含 12 个月的**月度明细**(按预算科目分行分月)。
- **版本化修订(Revision)**:同一(成本中心, 财年)可多版本(v1、v2…);修订生成新草稿指向父版本;只有 `is_current` 的版本被余额/实际查询读取;新版审批通过后父版自动退位(留痕)。
- **审批工作流**:草稿 → 提交 → 审核中 → 通过 / 退回 / 拒绝 / 取消;审批任务进 Finance 的 Task Inbox。
- 财务在 **Budget Plans / Budget Plan Detail** 页操作。

### 11.3 因子分解(Factor)与因子库
- 开了分解的预算科目,金额按**因子组合**填(如 {品牌, 渠道}),行金额 = 各组合之和。
- **因子库(Factor Library)**:管理员维护可复用的因子模板 + 取值;attach 到某预算科目时**复制**一份到该科目(复制后独立,改模板不影响已 attach 的历史)。
- 每个科目 1..N 个因子,上限由预算设置控制(默认 10,可调 1–50)。

### 11.4 预算执行台账(Budget Ledger)——预算与业务打通
- 一张**幂等台账**记录每一笔预算变动:**commit(占用)/ release(释放)/ actualize(实际)/ book_expense(费用入账)/ opening(期初)**。
- (来源服务 + 单据类型 + 单据 + 操作)唯一——EPMS/OA 重复推送被静默忽略(防重复扣预算)。
- 业务联动:采购申请(PR)审批**占用**预算 → 采购完成/取消**释放** → 报销/发票**实际**核销。台账是「预算已用/可用」聚合的事实源。

### 11.5 预算看板(Dashboard)
- 按成本中心/科目看 **预算 vs 占用 vs 实际 vs 可用**;EPMS 采购页也内嵌预算余额小组件做实时校验。

现状:**已上生产**(目录、按 CC 计划 + 版本修订 + 审批、因子分解 + 因子库、执行台账 + EPMS 联动、看板、设置)。

## 12. 预算 vs 实际(Budget Actual)打通

把「实际发生额」从**总账科目余额**取,按成本中心归类,和预算对比。

- **业务规则(财务定稿)**:实际由 **4 个费用科目**按成本中心归类:

  | GL 科目 | 费用类别 | 归入成本中心前缀 |
  |---|---|---|
  | 5101 制造费用 | MOH(制造) | `MOH-*` |
  | 5301 研发费用 | R&D(研发) | `RD-*` |
  | 6601 销售费用 | Selling(销售) | `SELL-*` |
  | 6602 管理费用 | G&A(管理) | `GA-*` |

- **实际口径 = 期间发生借方**(不是净额——制造费用期末结转,净额≈0)。

⚠️ **需财务重点核对**:4 个科目 + 成本中心归类是否正确、够用?是否也纳入 6603 财务费用等?
